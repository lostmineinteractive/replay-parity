# Changelog

All notable changes to this repository are recorded here. The format follows Keep a Changelog. Entries are grouped by build step while the project is unreleased.

## Unreleased

### Step 6: the rp command line

- Added `@replay-parity/cli` with the `rp` binary on commander. `rp capture` runs the recording proxy until SIGINT or SIGTERM with `--listen`, `--target`, `--out`, `--tag-rule`, `--sample`, `--redact-header`, `--max-body-bytes`, `--no-append`, and `--upstream-timeout-ms`. `rp replay` takes `--recording`, `--target`, `--out`, `--pace`, `--rps`, `--concurrency`, `--warmup`, `--filter tag=<name>`, `--limit`, `--rules`, `--thresholds`, `--adapter http|bus`, `--bus-url`, `--header`, `--headers-file`, `--barrier-tag`, `--barrier-timeout-ms`, `--candidate-recording`, `--invariants`, `--timeout-ms`, `--max-body-bytes`, and `--quiet`, writes the run, prints the terminal summary, and exits 0 on pass, 2 on fail, 3 on inconclusive, 1 on a tool error. `rp report` renders html, json, or terminal from a run, html when `--out` is given and terminal otherwise, and `--explain [exchange-id]` prints the plain language explanation of one exchange or of every mismatched exchange. `rp invariants` evaluates one recording and exits by the same code scheme. `rp shrink` reduces a failing run against a candidate reset through `--reset <url>`, writes the reduced recording, and updates the run file in place.
- Help text for every flag is written by hand. Usage errors, missing files, bad rule files, and bad header lines exit 1 with a message on stderr. Caller supplied headers come from `--headers-file` first and `--header` entries on top.
- A small `.env` reader, `loadDotEnv`, sets only variables that are not already set and never prints a value. `rp agent` uses it in Step 8.
- Tests: two unit files cover the `.env` parser and the option parsers. The integration file checks that the top level help lists every command and each command's help lists every flag with a description, the exit codes for unknown flags, missing required flags, missing files, bad values, and contradictory flags, a failing, a passing, and an inconclusive replay through the binary against the candidate in process with the written run validating against the schema, the three report formats, `--explain` for one and for all mismatches, the invariants command on the committed recording, a shrink through the binary that updates the run in place, and the capture proxy as a child process that records traffic and exits cleanly on SIGTERM.

### Step 5: report renderers

It has the header with the verdict badge and run facts, the inconclusive conditions, the threshold table, the invariants section per system placed above the diff, the latency section with a percentile table, the pacing line, and one histogram per tag plus overall with the reference drawn behind the candidate, the correctness section with counts by tag, the top mismatching paths, a drill down per mismatched exchange with the field level findings side by side, and the transport errors, the harness controls in sequence, the reproduction section, and the agent section when the run has one. Every recorded string is escaped.
- `renderJson` validates the run and pretty prints it. `renderHistogram` draws one bar per bin for each series over the 48 log spaced bins and labels the decade edges.
- Tests: 10 cover the terminal output with a snapshot, the HTML file's offline property and each section's presence and absence, escaping with a body that contains a script tag, the JSON round trip against the schema, and the determinism and bar count of the SVG. The word "minimal" never appears in either renderer's output.

### A4: shrinking (Addendum A4)

- Added `@replay-parity/shrink`. `shrink(options)` takes a recording, a candidate target, a reset hook, and a failing rule, and returns a reduced reproduction. The rule is either an invariant on one system (`invariant:<system>:<name>`) or a mismatching exchange with an optional finding path (`mismatch:<exchange id>[:<path>]`). `defaultRule(run)` picks the first violated candidate invariant, then the reference, then the first mismatching exchange.
- The algorithm. Steps after the witnessing exchange are dropped first. Delta debugging in the complement form then removes chunks of the remaining steps, and a prerequisite closure re-adds what any kept step needs: the create that produced an order id used in a path, and the producers named by the substitution rules. Relative order never changes and shipment ids are never renamed. For a candidate invariant a second pass lowers `qty` and `quantity` values toward one with a binary search per field. Every candidate reduction is replayed at `max` pacing with one request in flight against a candidate reset through the hook, and judged by the same rule. An attempt whose run is inconclusive counts as not reproduced.
- Bounds. `maxAttempts` (default 64) and `timeBudgetMs` (default 120000). When the budget runs out the best reduction confirmed so far is kept. When the first attempt does not reproduce, the original is kept and the label is `reduction unsuccessful`.
- Core: the run gains a nullable `reproduction` section with the rule, original and reduced step counts, attempts, `successful`, the label (`reduced reproduction` or `reduction unsuccessful`), the duration, the path of the reduced recording, and the steps with their bodies and a `quantity_reduced` flag. The JSON Schema is regenerated.
- Replay: `replayExchanges(exchanges, options)` replays a list held in memory and returns the run without reading a file. `replay(path, options)` reads the file and calls it. `writeExchanges` is exported.
- Tests: 15 in the package. Unit tests cover delta debugging with and without a closure, chunking, the budget error, rule parsing and formatting, the default rule, the judge, and the prerequisites. Integration tests shrink the committed recording against the candidate: the duplicate shipment defect reduces from 283 steps to at most five that still trip invariant 1 when replayed from the written file, the dropped pre cancel shipment reduces to create, cancel, and shipment, a rounding mismatch reduces to the single create that shows it, a rule that does not reproduce keeps the original, and both budgets stop the search while keeping what was confirmed.

### A1: independent invariants (Addendum A1)

- Added `@replay-parity/invariants`. `evaluateInvariants(exchanges)` evaluates the ten invariants against one system's recording and nothing else. A command parser maps exchanges to creates, cancels, quantity changes, shipments, stock adjustments, restarts, resets, and reads. A model rebuilds the expected state from the system's own acknowledgements: a command counts when the system answered 2xx, a rejected command is never applied, and a retried command is applied once. An accepted reset starts a new epoch and rules run per epoch.
- The rules, one file each, return `holds`, `violated`, `not_applicable`, or `inconclusive` with evidence naming the subject, the expected and observed values, and the witnessing exchange. Invariants 1 and 4 compare every order view with the expected quantity, shipped, remaining, and unshipped canceled quantity. Invariant 4 also expects a shipment that originated before the cancellation to be accepted and a later one to be rejected. Invariants 5 and 6 compare stock and receivable deltas between consecutive reads with the accepted adjustments and unique accepted shipments in that interval, so a shipment applied twice is localized to the interval where it happened. Invariant 5 reads initial stock plus accepted adjustments minus unique shipments. Invariants 8 and 9 check idempotency keys, retries, and order counts across the restart. Invariant 10 recomputes each allocation from a stock baseline derived from the first read of the SKU and the quantities live orders still have to ship.
- The completion check. When a state changing command was sent before the final ledger read and acknowledged after it, the report carries `snapshot_before_ack` and the run is inconclusive.
- Core: `InvariantReport` and its schemas, an `invariants` section on the run with `reference` and `candidate` reports, a `candidate_recording` path on the run, `invariants.fail_on_violation` in the thresholds file (default true), and threshold rows `invariants.reference.violations` and `invariants.candidate.violations`. The run JSON Schema is regenerated.
- Replay: the `invariants` option evaluates both recordings after the run, fills the section, forwards each report's inconclusive conditions, and feeds the violation counts to the thresholds. The engine now builds the candidate's observed log once and writes it when `--candidate-recording` is set.
- Tests: 22 in the package cover the parser, decimal arithmetic, every rule with a holding and a violating sequence, epochs, and the completion check, and the committed reference recording holds all ten invariants with nothing inconclusive. Seven integration tests in the replay package run the committed recording against the candidate with each seeded defect alone: `shipment-applied-twice` violates invariants 1, 5, and 6, `quantity-as-additional` violates 2 and 4, `drop-late-precancel-shipment` violates 4, and `idempotency-lost-on-restart` violates 8 and 9, each on the candidate only, while the clean pair holds everything.

### Step 4: replay engine

- Added `@replay-parity/replay`. `replay(options)` reads a recording, selects exchanges by tag and limit, sends them through an adapter on one of three schedules, diffs every response against the recorded one, aggregates statistics, evaluates the thresholds, and returns the run. `as-recorded` keeps the recorded gaps, `fixed-rate` spaces sends at `--rps`, and `max` sends as soon as a slot in the pool is free. Each exchange result carries `scheduled_at_ms`, `sent_at_ms`, and `acked_at_ms`, and the run carries requested and achieved rate with schedule slip p50 and max.
- Substitutions. A `DependencyIndex` computes, before anything is sent, which earlier exchange produces each captured value a request uses, and the engine waits for those producers under every pacing mode. A `SubstitutionTable` records reference to candidate pairs as exchanges complete, rewrites later paths, query values, and body leaves, and feeds the differ its equivalences so a mapped id is reported as tolerated by `substitution:<name>`. The first exchange to produce a reference value wins, so a retried command that yields a different candidate id is a mismatch rather than a silent remap.
- Barriers. `--barrier-tag` (repeatable) and `--barrier-timeout-ms` (default 10000). An exchange with a barrier tag waits until every earlier exchange has a response or an error, is sent alone, and is acknowledged before anything later is sent. A wait longer than the timeout records `barrier_timeout` and the run is inconclusive. The run records `barrier_tags`, `barrier_timeout_ms`, and `barrier_waits`.
- Harness controls. The rules file gains `controls.tags`. An exchange carrying one of these tags is a barrier, is diffed on status only through the new `differ.diffStatus`, is excluded from statistics and from every threshold, and is written to the run with `control: true` so the report can show it in sequence without scoring it. A control that fails or answers a different status makes the run inconclusive with the new kind `control_failed`.
- HTTP adapter on an undici pool. Sends the recorded method, path, query, headers, and body, drops hop by hop headers, the host, the content length, and any header whose recorded value is `<redacted>`, applies caller supplied headers over recorded values, measures latency from dispatch to the last body byte, enforces the timeout through an abort signal so the deadline is exact, and classifies failures as `timeout`, `connection`, `aborted`, `protocol`, or `other`.
- Bus adapter over a `MessageBus` interface with string payloads. `InProcessBus` delivers asynchronously in publish order. `RedisStreamsBus` publishes with `XADD` and reads with a blocking `XREAD` on a dedicated connection, loading the `redis` client on first use. The adapter publishes a request envelope with a correlation id to `rp.requests.<first path segment>` and awaits the reply envelope on its own reply topic. `serveBus` is the responder side, used by the tests and documented as the contract for a system under test.
- `--candidate-recording <path>` writes the requests as sent and the candidate responses as a second recording in the same format, in send order, with the reference exchange ids and tags, and with the capture redaction list applied to headers. Failed sends are left out.
- Warmup exchanges run but are excluded from statistics. Transport failures are recorded as `error` with a null candidate and a null diff. A truncated recorded body is never diffed and yields one `body_too_large` finding that counts as a mismatch.
- Core: `DiffRulesSchema` gains `controls.tags`, `Differ` gains `diffStatus`, `InconclusiveKind` gains `control_failed`, and the run JSON Schema is regenerated.
- Tests: 42 across the package. Unit tests cover the schedules, slip summary, dependency index, substitution table, header and query helpers, both buses, and the bus adapter. Integration tests run the committed recording against the candidate in process: the clean pair passes with zero mismatches and a valid run and candidate recording, shifted ids pass through substitutions, barriers hold order under concurrency, the four classic divergences are found and the `adjust-stock` p99 gate fails with the seeded delay, filter and limit and warmup apply, each pacing mode holds its schedule, a barrier timeout and a failed control make the run inconclusive, transport failures are recorded, and caller supplied headers override recorded ones. The Redis Streams test runs when `REDIS_URL` is set.
- Added `DEFERRED.md` for work noticed during the build that is out of scope for the current step.

### A2: inconclusive verdict in core (Addendum A2)

- The run verdict is now `pass`, `fail`, or `inconclusive`. A new `inconclusive` array on the run lists the triggering conditions, each with a `kind` (`barrier_timeout`, `snapshot_before_ack`, `schedule_not_held`, `insufficient_samples`) and a `detail` string. `decideVerdict` in `run/verdict.ts` applies the precedence rule: a run level condition makes the run inconclusive even when mismatches were observed, otherwise any failed threshold or invariant violation makes it fail, otherwise any insufficient sample row makes it inconclusive, otherwise it passes. `EXIT_CODES` maps pass to 0, fail to 2, inconclusive to 3, and tool error to 1.
- Threshold rows carry `outcome` (`pass`, `fail`, `inconclusive`) instead of `pass: true | false`. A latency row with fewer successful candidate samples than its minimum, a `by_tag` entry whose tag is absent, a correctness row with nothing compared, and an error rate row with no samples are inconclusive rather than failed. A ratio row with a zero reference value still fails, since that is a fact about the data.
- The thresholds file gains `latency.min_samples` (default 1), an optional `min_samples` override inside `overall` and each `by_tag` entry, and a `pacing` section with `slip_max_ms`. When `slip_max_ms` is set and the replay's largest schedule slip exceeds it, the run is inconclusive with `schedule_not_held`. When unset, slip is reported and never triggers.
- The run model gains `pacing.barrier_tags`, `pacing.barrier_timeout_ms`, `pacing.barrier_waits`, and per exchange `acked_at_ms` and `control`. Step 4 fills them. `control: true` marks a harness control such as a restart, which is replayed in order and shown in sequence but never scored. The fixture builder excludes control exchanges from statistics.
- `packages/core/schema/run.schema.json` regenerated.
- Tests: 14 new or changed cases across the evaluator, the verdict rule, the thresholds schema, and the run model. 228 tests pass across the workspace.

### Step 3b: order lifecycle in the demo services (Addendum A0)

- Both demo services gain `Idempotency-Key` on `POST /v1/orders`, `POST /v1/orders/:id/cancel`, `POST /v1/orders/:id/quantity`, `POST /v1/orders/:id/shipments`, `GET /v1/ledger` with decimal strings, and the admin controls `POST /admin/restart` and `POST /admin/reset`. Orders carry `status` (`OPEN`, `PARTIALLY_SHIPPED`, `SHIPPED`, `CANCELED`, `REJECTED`), `quantity`, `shipped`, `remaining`, and `canceled_unshipped` next to the amount in `total`. Stock on hand changes only on accepted shipments and adjustments. Creation allocates against available stock and a shortfall yields a `REJECTED` order. Cancellation acceptance is the cancel request's own `originated_at`.
- A `Store` keeps the working state in memory and commits every mutation to a durable copy, a JSON file when `STORE_PATH` is set. `restart` reloads the durable copy, which is what a process restart does.
- The candidate's `DIVERGENCES` switch is now a named set. `on` enables the original four (`rounding-half-even`, `inventory-insertion-order`, `adjust-stock-delay`, `unknown-order-200`), `off` enables none, and a comma separated list enables exactly the named ones. The four seeded defects of Addendum A3 are present as marked lines: `shipment-applied-twice`, `quantity-as-additional`, `drop-late-precancel-shipment`, `idempotency-lost-on-restart`.
- The candidate `app.ts` is derived from the reference `app.ts`. `scripts/check-parallel.sh` fails when the two differ outside hunks marked `DIVERGENCE` or `DEFECT`, or when `store.ts` or `catalog.ts` differ at all.
- The load generator now runs a seeded plan of twelve lifecycle scenarios with background traffic between them, a ledger read after each, and a final read of every order and the ledger. New tags: `cancel-order`, `set-quantity`, `ship-order`, `list-ledger`, `admin-restart`, `admin-reset`.
- `demo/recording.jsonl` regenerated: 283 exchanges over 12.8 seconds, 44 orders, nine tags, seven retried idempotency keys, one restart.
- `scripts/check-prose.sh` no longer bans `ledger`, since the route name is mandated by the addendum.
- Tests: 42 across the two services and the load package cover every lifecycle route, idempotency, cancellation by `originated_at`, duplicate shipments, allocation, the store across an in memory restart and a real rebuild, each seeded defect alone, byte identical parity with divergences off over every route, and the plan's shape.
- PLAN.md gains section 8, the Addendum A plan, with the approval record.
