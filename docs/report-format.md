# The run file

`rp replay` writes `run.json`. It is the canonical report. `rp report` renders HTML and the terminal summary from it, `rp shrink` and `rp agent` add their sections to it in place, and `rp report --format json` validates it and prints it again. The JSON Schema, draft 2020-12, is generated from the zod definitions in `packages/core/src/run/schema.ts` and committed at `packages/core/schema/run.schema.json`. A test fails when the two drift apart.

Schema versions. `rp` migrates an older run file when it reads one: before validating against the schema, it applies one migration per version step from the file's `schema_version` up to the current one, so a file written by an earlier `rp` still renders and can still be extended by `rp shrink` and `rp agent`. A file whose `schema_version` is higher than the one this `rp` knows is refused with an error saying it was written by a newer version of `rp`, and a file with no integer `schema_version` is refused with an error naming that. The migrations live in `packages/core/src/run/migrate.ts`, one entry per source version in `RUN_MIGRATIONS`.

Version 2 added the exchanges sidecar. The migration from version 1 sets `exchanges_path` to null, since a version 1 run holds every exchange in the file. The other fields version 2 added are optional and stay absent in a migrated run: `reference_target`, the `pacing` fields `session_key`, `sessions`, `speed`, `loop`, and `retry`, the exchange fields `attempts`, `first_error`, and `reference_now`, the finding field `noise`, and the statistics `retried` and `noise_findings`. A reader treats an absent field as the feature being off.

Version 3 added the baseline. The migration from version 2 sets `baseline` to null, since a version 2 run was never compared with one. The other fields version 3 added are optional and stay absent in a migrated run: the statistics field `candidate_status`, the condition flag `tolerated`, and the threshold sections `throughput`, `status`, `baseline`, and `inconclusive` with the per tag `relative_to_reference.by_tag` and `errors.by_tag`. A run without `candidate_status` cannot decide a `status` row, which is then inconclusive with the kind `not_measured`.

## Verdict and inconclusive kinds

The precedence rule: a run level condition makes the run inconclusive even when mismatches were observed. Otherwise any failed threshold row makes it fail. Otherwise any insufficient sample row makes it inconclusive, unless the `inconclusive.max_rows` budget tolerated it. Otherwise it passes. A tolerated condition stays in `inconclusive` with `tolerated: true`, so a passing run can list conditions; a run level condition is never tolerated.

| Kind                   | Run level | Set when                                                                                                                                                                                                                       |
| ---------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `barrier_timeout`      | yes       | An exchange with a barrier tag waited longer than `--barrier-timeout-ms` for earlier exchanges.                                                                                                                                |
| `snapshot_before_ack`  | yes       | The final ledger read was sent while an accepted state changing command was still in flight. Reported by the invariants.                                                                                                       |
| `schedule_not_held`    | yes       | The largest schedule slip exceeded `pacing.slip_max_ms`.                                                                                                                                                                       |
| `control_failed`       | yes       | A harness control errored or answered a different status.                                                                                                                                                                      |
| `aborted`              | yes       | The run was stopped by SIGINT or SIGTERM. The detail says how many of the selected exchanges were sent; the rest are left out of `exchanges`.                                                                                  |
| `insufficient_samples` | no        | A threshold row could not decide: fewer successful samples than `min_samples`, a tag with no samples, nothing compared, or no samples at all, in this run or in the baseline. The only kind the inconclusive budget tolerates. |
| `not_measured`         | no        | A threshold row needs a measurement the run did not take: the achieved rate, the candidate statuses, or the noise of a reference re-replay.                                                                                    |

## Threshold rows

Each row has `id` (such as `latency.by_tag.create-order.p99_ms`), `section` (`latency`, `correctness`, `errors`, `throughput`, `status`, `baseline`, `pacing`, `invariants`), `scope` (`overall`, a tag, or a system), `metric`, `limit`, `measured` (a number or null), `outcome` (`pass`, `fail`, `inconclusive`), and an optional `detail` such as `3 successful samples, minimum 20`. docs/thresholds.md lists every row id and when each row is inconclusive. In a run that used `--reference-target`, every mismatch rate row has the detail `N noise findings excluded`.

## Statistics

`stats.overall` and `stats.by_tag.<tag>` have the same shape: `count`, `errors`, `error_rate`, `compared`, `matches`, `tolerated`, `mismatches`, `mismatch_rate`, `candidate` and `reference` latency summaries (`count`, `p50_ms`, `p90_ms`, `p99_ms`, `p999_ms`, `max_ms`, `mean_ms`), `histogram` with `candidate` and `reference` bin counts, and `candidate_status`: compared exchanges per candidate status code, keyed by the code as text, as in `{ "200": 101, "404": 8 }`, absent in a run written before the field existed. `stats.histogram_edges_ms` holds the 49 edges of the 48 log spaced bins from 0.1 ms to 10 s, so the HTML renders the histograms without a library. Warmup and control exchanges are excluded. Reference latencies come from the recording.

Two counts sit beside them, each present only when the run used the feature that produces it, and each with `overall` and `by_tag.<tag>` over the same counted exchanges:

- `stats.retried`, with `--retry`: the exchanges that were sent more than once, whatever the last attempt returned. An exchange that passed only on a retry is counted here, so a pass on retries cannot hide a candidate that drops requests.
- `stats.noise_findings`, with `--reference-target`: the findings the reference re-replay marked as noise.

## Exchange results

| Field                                          | Meaning                                                                                                                                                                                                                       |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`, `tags`, `method`, `path`                 | From the recording. The path is the recorded one, before substitution.                                                                                                                                                        |
| `warmup`                                       | True for the leading warmup exchanges.                                                                                                                                                                                        |
| `control`                                      | True for a harness control.                                                                                                                                                                                                   |
| `dependency`                                   | True for an exchange selected only because a filtered exchange uses a substituted value it produces. Replayed and acknowledged for ordering and substitution, excluded from statistics and thresholds like a warmup exchange. |
| `scheduled_at_ms`, `sent_at_ms`, `acked_at_ms` | Milliseconds since the run started. `acked_at_ms` is null on an error.                                                                                                                                                        |
| `reference`                                    | `status` and `latency_ms` from the recording.                                                                                                                                                                                 |
| `candidate`                                    | `status` and `latency_ms` from the replay, or null on an error.                                                                                                                                                               |
| `error`                                        | `kind: message` on a transport failure, else null. Kinds: `timeout`, `connection`, `aborted`, `protocol`, `other`.                                                                                                            |
| `diff`                                         | `verdict` (`match`, `tolerated`, `mismatch`) and `findings`, or null when not compared.                                                                                                                                       |
| `attempts`                                     | How many times the request was sent, present only when it was retried. `error` and `candidate` describe the last attempt.                                                                                                     |
| `first_error`                                  | The transport failure of the first attempt, present only when the request was retried.                                                                                                                                        |
| `reference_now`                                | With `--reference-target`: the reference's `status` and `latency_ms` on the re-replay of this exchange, or null when the reference did not answer. Absent otherwise.                                                          |

A finding has `path` (a concrete JSONPath, `status`, or `header:<name>`), `kind` (`status`, `header`, `value`, `type`, `missing`, `unexpected`, `body_too_large`, `body_format`), `tolerated`, and optional `reference`, `candidate`, `rule`, `detail`, and `noise`. `noise: true` marks a finding the reference re-replay tolerated; it also has `tolerated: true` and the rule `noise:reference`. A tolerated finding names its rule as the rules file numbers it, such as `tolerances[1]`, `decimal[0]`, `time[2]`, `mask[0]`, `status.equivalent[0]`, `headers.masks[0]`, `extra_fields`, `extra_fields_rules[1]`, `equivalences.null_absent`, or `substitution:order_id`, and for the newer rule kinds `detail` states the reason, as in `equal after rounding to 2 places`; docs/diff-rules.md lists every name. A row matched under a keyed `unordered` rule appears in the path as `[name=value]`, as in `$.items[sku=A-100].qty`. The key value is bare for a string that is a plain identifier such as `A-100` and for a number, `true`, `false`, or `null`, a JSON string in double quotes for any other string, as in `$.items[sku="a b"].qty` and `$.items[sku="1"].qty` for the string `1` against `$.items[sku=1].qty` for the number, and the canonical JSON in single quotes for an array or object, as in `$.items[sku='[1,2]'].qty`; the name is quoted as a JSON string when it is not an identifier; the nth later row with the same key carries `#n` after the value, as in `[sku=A-100#1]`; and a row without the key is grouped by its own canonical JSON in single quotes behind `#`, as in `[sku=#'{"qty":3}']`. Every finding path reads back through the harness's JSONPath parser.

Bodies in the recording and in the candidate recording follow one rule set. A JSON content type is stored parsed in `body`. Anything else is stored as base64 in `body` with `encoding: "base64"`. A body over the size cap is stored as `truncated: true` with `body_sha256` and `body_size`. A body that arrived with a `content-encoding` of gzip, deflate, or br is decoded first, stored by the same rules, and carries `content_encoding` with the codings undone, in the order they were applied. The cap applies to the decoded size, and a truncated body's hash and size always describe the bytes as received. A coding the harness cannot undo, or data that does not decode, is stored as received with no note.

## Reference re-replay

With `--reference-target <url>` every exchange is sent to the reference as well as the candidate, at the same moment and in the same order, prepared from the reference's own substitution table, which is built from the reference's answers. For each exchange the recording is diffed against the reference's answer first, and every untolerated path there is noise: the reference moved there by itself, as a timestamp or a fresh id does. The recording is then diffed against the candidate, and every untolerated finding at a noise path gets `tolerated: true`, `rule: "noise:reference"`, and `noise: true`, so the verdict does not count it. A finding at any other path stands.

A reference that answered a different status than the recording, a body of another format, or a body too large to compare names no noise for that exchange, and neither does a reference that did not answer, so a reference that fails never excuses a candidate that fails the same way. The candidate's findings then stand as they are. Harness controls are sent to both systems and diffed on status only, without noise.

## Exchanges sidecar

With `--exchanges-sidecar`, and by default when the run has more than 50000 results, every exchange result streams to `<out>.exchanges.jsonl` next to the run file, where `<out>` is the run file's path without `.json`: `run.json` gives `run.exchanges.jsonl`. Each line is one exchange result as described above, in recording order. The run file then holds the summary, `exchanges_path`, and in `exchanges` the first 20 mismatched exchanges of each generalized path, the generalized path of an exchange being that of its first untolerated finding with array positions folded into `[*]`, which is how the HTML drill down groups them. Controls are not kept. `--no-exchanges-sidecar` keeps every result in the run file however many there are.

`rp report` reads the sidecar when `exchanges_path` is set and the file is there, and renders every format from the whole run. `--format json` prints the run file itself. When the sidecar is missing the report says so on stderr and renders the exchanges the run kept.

## Checkpoint

A run that uses the sidecar writes `<out>.checkpoint.json` every 1000 acknowledgements and when it is stopped, and removes it when it finishes. `rp replay --resume` with the same recording and options continues the run from it. The checkpoint is a JSON object:

| Field                                                         | Meaning                                                                                                                                                                                               |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `checkpoint_version`                                          | `1`.                                                                                                                                                                                                  |
| `run_id`                                                      | The run's id, which the resumed run keeps.                                                                                                                                                            |
| `fingerprint`                                                 | The recording's path and hash, the target, the reference target, and every option that shapes the selection or the results. A resumed run whose fingerprint differs is refused, naming the field.     |
| `next_index`, `last_index`                                    | The first exchange the resumed run sends and the last one of the acknowledged prefix, counted over the whole run from 0. A send the stop cut short is not part of the prefix.                         |
| `sidecar`                                                     | `path`, and the `bytes` and `lines` of the sidecar that hold the prefix. The resumed run truncates the sidecar to `bytes`.                                                                            |
| `elapsed_ms`                                                  | When the prefix ended, so the resumed run's times continue from it.                                                                                                                                   |
| `table_iteration`, `substitutions`, `reference_substitutions` | The substitution tables as the prefix left them, for the iteration of its last exchange: per rule, the reference value, the candidate value, and the position of the exchange that produced the pair. |
| `conditions`, `barrier_waits`                                 | The inconclusive conditions and the barrier waits of the prefix.                                                                                                                                      |
| `stats`                                                       | The prefix's counts: `results`, `counted`, `errors`, `matches`, `tolerated`, `mismatches`. The resumed run rebuilds its statistics from the sidecar and refuses one that does not add up to them.     |

## Invariant reports

Each report has `system`, `recording`, `exchanges`, `commands`, `snapshots` (`ledger_reads`, `stock_reads`, `order_reads`), `results`, `violations`, and `inconclusive`. Each result has `id` (1 to 10), `name`, `statement`, `status` (`holds`, `violated`, `not_applicable`, `inconclusive`), `checks`, `evidence`, and an optional `detail`. Evidence entries have `subject`, `expected`, `observed`, `detail`, and `exchange_id`.

## Reproduction

Written by `rp shrink`; see `docs/shrinking.md` for how the reduction is found.

| Field            | Type            | Meaning                                                                                                                                                              |
| ---------------- | --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `rule`           | string          | `invariant:<system>:<name>`, `mismatch:<exchange id>[:<path>]`, or `latency:<tag>:<metric>`.                                                                         |
| `original_steps` | integer         | Steps in the recording.                                                                                                                                              |
| `reduced_steps`  | integer         | Steps that remain.                                                                                                                                                   |
| `attempts`       | integer         | Replays spent, each after a reset. With `--targets`, replays that ran ahead of the chunk that was taken are not counted. Zero when every answer came from the cache. |
| `successful`     | boolean         | True when the steps are fewer than the original or a value was lowered, and the rule still reproduces.                                                               |
| `label`          | string          | `reduced reproduction`, `reduced reproduction (statistical)` for a latency rule, or `reduction unsuccessful`. The label never says minimal.                          |
| `duration_ms`    | number          | Time the shrink took.                                                                                                                                                |
| `recording`      | string or null  | Path of the reduced recording, or null when none was written.                                                                                                        |
| `repeat`         | integer         | Optional. Present for a latency rule: how many times each attempt replayed its subset, so the judgement is over the pooled sample.                                   |
| `cache_hits`     | integer         | Optional. Present when attempts were answered from the cache without a replay.                                                                                       |
| `steps`          | array of object | The remaining steps in recorded order.                                                                                                                               |

Each step has `id`, `method`, `path`, `tags`, an optional `body` (the body as sent, with lowered and simplified values), `quantity_reduced` (true when a lowered integer was reduced), and an optional `changed`: a list of `{ path, from, to }`, one per value that differs from the recording. `path` is the concrete JSONPath in the body, such as `$.items[1].quantity`, `from` is the recorded value, and `to` is the value that was kept. `changed` is absent when nothing changed.

## Agent

`model`, `rounds`, `max_rounds`, `budget_usd`, `cost_usd`, token counts (`input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`), `proposed`, `valid`, `executed`, `kept`, `stop_reason` (`no_new_cases`, `budget`, `max_rounds`, `no_valid_cases`, `model_refusal`, `error`, or `aborted` when SIGINT or SIGTERM stopped the loop at a case boundary), `prompt_versions`, `transcript_path`, `cases_path`, and `cases`. Each kept case has `id`, `round`, `hypothesis`, `tags`, `steps`, `repeat` (how many times the case ran on each system, 1 to 50), `dedupe_key`, `reference` and `candidate` (status and latency of the final step of the first run, or null), `latency` (exact nearest rank percentiles over the runs of each side, in the same shape as a latency summary, or null when a side failed), `error`, `diff`, `latency_breach`, and `revealed`.

## Output formats

`rp report --format <name>` renders the run file in one of five formats. Without `--format` the command writes HTML when `--out` is given and the terminal summary otherwise. Every format is rendered from the run file alone, so the same run always produces the same bytes.

| Format     | Use                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `terminal` | The plain text summary `rp replay` prints. No color codes, so it reads the same in a log.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `html`     | One file with inline CSS and inline SVG, no script, no external resource. The correctness drill down shows at most 200 mismatched exchanges. They are grouped by the generalized path of their first untolerated finding, in the order of the top mismatching paths, and taken round robin across the groups in run order, so every path is represented even when one path accounts for nearly every mismatch. Each group heading says "showing N of M", and a line above the groups says how many were left out. The errors table lists at most 50 and says so. The full lists are in the run file, or in its exchanges sidecar when the run used one. |
| `json`     | The run file itself, validated against the schema and pretty printed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `junit`    | JUnit XML for a CI system. See below.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `markdown` | A summary for a pull request comment or a GitHub job summary. See below.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |

### JUnit

`--format junit` writes one `<testsuites>` document that GitHub Actions test reporters, Jenkins, and GitLab accept. Every value from the run is escaped, control characters XML cannot carry are dropped, and nothing depends on the clock.

- One `<testsuite>` per threshold section that has rows, named `latency`, `correctness`, `errors`, `throughput`, `status`, `baseline`, `pacing`, or `invariants`, in that order. Each row is a `<testcase>` with `classname` set to the section and `name` set to the row id, such as `latency.by_tag.create-order.p99_ms`. A failed row carries a `<failure>` whose message is `measured X, limit Y`; a row that could not decide carries a `<skipped>` whose message is the row's detail, such as `3 successful samples, minimum 20`, prefixed with `tolerated by the inconclusive budget: ` when the budget tolerated it.
- One `<testsuite>` per system with invariant results, named `invariants.reference` and `invariants.candidate`, with one `<testcase>` per rule named after the rule. A violated rule carries a `<failure>` whose message is the first evidence line and whose body lists the statement and every evidence entry. An inconclusive or not applicable rule carries a `<skipped>`.
- One `<testsuite name="run">` with a single `<testcase name="verdict">`. It fails on a failing run with the failed rows in the body, is skipped on an inconclusive run with the conditions as the message, and passes otherwise. Its `<properties>` carry the run id, the verdict, the recording, the target, the creation time, and the baseline when the run had one.

A passing run therefore shows every case green, a failing run shows exactly the rows and rules that failed, and an inconclusive run shows what could not decide without counting it as a failure.

### Markdown

`--format markdown` writes GitHub flavored Markdown with no HTML: a heading with the verdict and the run id, the recording, target, pacing, and duration, the baseline when there was one, the inconclusive conditions when there are any and apart from them the conditions the inconclusive budget tolerated, the threshold table, the latency table with reference / candidate p50, p99, and max per tag, the correctness totals and the top mismatching paths, the invariant summary per system with every violated or inconclusive rule, the reproduction when `rp shrink` ran, and the agent summary when `rp agent` ran. Recorded strings have their Markdown punctuation escaped so a path or a hypothesis cannot break a table. The demo run renders in well under 150 lines. Write it to `$GITHUB_STEP_SUMMARY` for a job summary, or post it as a pull request comment.

### Exit code after a render

`rp report` exits 0 after a successful render whatever the verdict, so a pipeline can always produce the report. With `--fail-on-verdict` it exits with the run's own code instead, 0 for pass, 2 for fail, and 3 for inconclusive, after the output is written. The flag applies to every format and to `--explain`. A tool error such as a missing run file still exits 1. A pipeline that wants to render first and gate second runs `rp report` twice, or once with the flag as its last step.
