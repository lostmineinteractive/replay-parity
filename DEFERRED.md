# Deferred

Items noticed during the build that are out of scope for the current step go here, each naming the step that raised it and what would change. Nothing here is required for `make demo`.

The six items this file held after Step 9 (compressed bodies, Redis Streams in CI, grouped top paths, agent dedupe granularity, prompt caching, and volume for latency cases) were done afterwards and are recorded in `CHANGELOG.md` under the heading for the work after Step 9. The items the two waves of the second enhancement round, `ENHANCEMENTS_2.md`, left here that wave three then did are removed, and `CHANGELOG.md` records them under "Enhancements, round two: wave three". They are progress during a replay, the TLS flags on `rp agent` and the transport options, `rp recording anonymize` and `migrate`, and the agent CLI test that left files in the working directory. Each item below names the enhancement that raised it.

- `rp recording diff` (E2). The command compares two recordings exchange by exchange under the rules. It waits on a decision about what two recordings compared under the rules should report. `rp recording` ships `validate`, `stats`, `filter`, `sample`, `split`, `merge`, `scan`, `migrate`, and `anonymize`.
- The run file does not record the effective configuration (E11) or the agent's isolation mode (E9). `rp doctor` prints the configuration and profile in effect, and the agent transcript records the isolation mode under `isolation`, but a run file alone does not say which file, profile, or variables produced it or whether the agent's cases ran with resets or in parallel. A run store (E17) would need both to index runs, and `ENHANCEMENTS_2.md` named them as what the run should carry.
- `rp report` does not display `recording.recording_sha256` (E2). The field is in the run file and `rp shrink` and `--baseline` check it, and none of the five renderers prints it. Showing it in the header of the HTML, the terminal summary, and the Markdown would let a reader tie a report to a recording without opening the run file.
- A README per package for npm (E14). The eight public packages ship `dist/src`, the root `LICENSE`, and for core and agent their `schema/` and `prompts/`, and no package has a README of its own, so each package's page on npm carries only the `description` field of its `package.json`. `docs/release.md` describes the libraries, and a short README per package pointing there would be the fix.
- The root `Dockerfile` is untested (E14). `scripts/release-check.sh` builds the image only when a Docker daemon answers, and none was available when the release work was done, so the image has not been built locally. The release workflow builds and pushes it on the first version tag, which is where it will be exercised first; `make image` builds it locally once a daemon is available.
- The vitest worker stall on macOS (E15). On the macOS development machine a vitest worker stalls for about 9 seconds when another suite runs at the same time, which is what made synchronous tests of a few hundred milliseconds take 7 seconds and the three pacing tests fail before they were rewritten. The likely cause is process scheduling or timer throttling of forked workers, and the options to try are `pool: threads` or fewer workers in the CI configuration. The timing policy in `docs/testing.md` makes the suite pass under the stall, and the tests that still carried a plain elapsed bound now follow it, so the root cause is the only open part.
- Lifecycle prerequisites for a filtered replay (E3, from the hardening table). `--filter tag=get-order` now pulls in the `create-order` exchanges that produce the ids, so no read mismatches on its id or status, but a read that followed a shipment, a cancel, or a quantity change in the recording still differs on `$.status`, `$.shipped`, `$.remaining`, `$.canceled_at`, `$.canceled_unshipped`, `$.items[0].qty`, `$.quantity`, and `$.total`, 27 mismatches on the committed recording, because nothing those reads use is a substituted value. Selecting every earlier command on the same order would need a lifecycle aware prerequisite rule beyond the substitution rules, and was left out; the test in `packages/replay/test/engine.int.test.ts` pins the remaining findings to those paths. `docs/troubleshooting.md` shows how to cut a recording that keeps the lifecycle commands as a workaround.
- Verifying the suite on Windows (E14). The `unit-matrix` job runs the unit project on `windows-latest` with `continue-on-error`, so its result is shown and never blocks a merge. The first failure there, the committed recording's pinned hash changing with CRLF line endings, was fixed with the rules in `.gitattributes`. Once a run there has been read and any other path or line ending issue fixed, the job should block like the other two.
- A streamed request body is never retried (E1, accepted). The proxy pipes the client's body upstream as it arrives, and undici cannot retry a streamed body, so a request whose upstream connection fails mid upload is answered 502 and recorded as a failure rather than sent again. This was accepted when streaming landed and is noted here so nobody looks for a retry.
- Distributed workers (E3). A coordinator would split a recording by session, hand the shards to `rp replay --worker` processes on other hosts over a small HTTP protocol, and merge the runs into one. A replay runs in one process today, and the other items of E3 do not depend on this one.
- `--duration` and `--ramp` for `rp replay` (E3). `ENHANCEMENTS_2.md` proposed `--duration` to repeat a recording for a length of time and `--ramp` to raise a fixed rate. `rp replay` has `--speed`, `--loop`, and `--max-gap-ms`, and neither flag exists. `rp capture` has its own `--duration`.
- The `envoy-tap` and `otel-spans` importers and the recorder plugins (E1). `rp import` reads HAR 1.2 only. The importers for Envoy taps and OpenTelemetry spans, and the recorder as a Fastify and an Express plugin for a team that owns the reference, are not built.
- Redaction of ids in URL paths (E1, E13). Capture rules cover body fields, query parameters, and headers. An id that also appears in a path segment stays in clear there, and a hashed id captured from a body does not match it, so a substitution through a hashed id works only when the id travels in bodies or query parameters. Redacting a path segment would need a rule form for paths and a decision about how a substitution reads it.
- `$num` values in substitution captures and unordered keys (E2, E4). A substitution captures strings and plain numbers, so an id that is a lossless number is not captured, and ids too large for a double are best sent as strings. An unordered rule keys a row by the text of its key value, so rows keyed by `{"$num": "1.10"}` and `{"$num": "1.1"}` do not pair, although the differ compares those two numbers as equal elsewhere.
- Manifests through `rp recording filter`, `sample`, `split`, and `merge` (E2). Each reads a manifest and drops it, and writes a recording with no manifest line, so a derived file no longer says which tool, target, tag rules, redaction, and sampling produced the original. `rp recording migrate` adds one by hand. Carrying the manifest through, with a note of the operation, would keep the provenance.
- The shrink cache is not keyed on the candidate's version (E8). The attempt cache keys an attempt by the subset, the rule, and the replay settings, and the module identity of an invariant module. Nothing in the key says which build of the candidate answered, so a cache file kept across a deploy answers with verdicts for the old build. Use a new cache file after the candidate changes. A key that includes a version string given on the command line would remove the hazard.
- `--preflight-probe` with `--targets` probes the first target and the first reset URL only (E8). The other candidates are first reached by the shrink itself.
- Declarative conservation keyed inside arrays (E6). A `conservation` rule reads one key and one value from single paths of one exchange. A read whose body is an array of keyed rows, such as one balance per account, is not tracked per row, and the rule would need a way to name the key and the value inside each element.
